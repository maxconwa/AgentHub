# Prompts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The operator's **Prompt** wakes the right agents now: one agent starts a session on it right away (or right after its current session), and several agents talk it over, split the work by who is free and what their machine has, and each turn their share into an already-approved task.

**Architecture:** The hub records each prompt and one row per recipient (`hub/prompts.py`, migration 14) and pushes `prompt.created` to the recipients. Runners pick up their pending prompts with priority over new task sessions and run a prompt session: a direct one for a single recipient, and a discussion session for a group, which ends with each agent claiming a share (a new task) or declining. The dashboard gets a **Prompt** button next to every **Send** and shows each prompt's progress.

**Tech Stack:** Python 3.12, FastAPI, SQLite, Jinja2 + HTMX, the runner (`claude -p`), MCP SDK v2, pytest.

**Spec:** `docs/superpowers/specs/2026-10-21-dashboard-redesign-design.md` — "Talking to agents from anywhere" (Prompt, idle/busy behaviour, several agents), "Agents can ask the operator" (the answer wakes the agent), Constraints 6 (coordination reuses the existing mechanism) and 7 (several agents per task), the panel and chat-window section (Send and Prompt in every composer).

## Global Constraints

- Only the operator creates prompts (`PostOp` routes, CSRF). Agents can't create or forge them. The prompt body reaches agents as operator text, outside the untrusted block, headed `From the operator (prompt #N, verified by the hub):`.
- Recipients come from `views.recipients(target)` (Task 9 of the pages plan): agent → that agent; task → its agents; project → agents on its live tasks; device → agents on that machine. Only active agents; **offline recipients are skipped** and the operator is told which ones on the prompt's status.
- **Idle agent:** its runner starts the prompt session right away. **Busy agent:** it finishes its current session first, then the prompt runs before any new task session. The operator can still stop a running session (existing behaviour).
- **Several agents:** they discuss as equals in one shared thread, weighing who is free versus busy and what each machine has, agree on a split, and **each agent's share becomes a task** that is already approved (it came from the operator), with its own budget, assigned to that agent with role "Share of prompt #N". The agreement is recorded where the operator sees it.
- Prompt sessions are subscription-only like every session (`BILLING_ENV_VARS` scrubbed), run in the runner's permission mode, and hit the usage limit the same way tasks do (pause, then resume).
- Prompt sessions have their own budget from `runner.toml`: `prompt_max_turns = 40`, `prompt_wall_clock_minutes = 30` (defaults).
- Group discussions time out after `prompt_discussion_minutes = 30` (hub.toml, default). Recipients that haven't claimed or declined by then are marked timed out, and the operator is told.
- Every new `/ui` route is operator-only and covered by the route walk; every new agent API route requires an active agent; agent text is labeled and rendered with `md`; no inline script or style.

## Review Focus

1. A busy agent: the prompt must not run alongside its current session or be lost; it runs as soon as that session ends, before new task sessions.
2. A runner that restarts mid-prompt: the prompt is resumed or marked failed with the operator told, never silently dropped (nothing lost on restart).
3. Two agents claiming overlapping shares, or one agent claiming twice: each claim makes exactly one task; a second claim from the same agent replaces nothing and is refused.
4. An offline or revoked recipient, or every recipient offline: the operator sees it at once; nothing waits forever.
5. An agent trying to create a prompt, claim a share of a prompt it isn't a recipient of, or read another prompt: refused.

### Task 1: Prompts on the hub (model, API, events)

**Files:** Modify `hub/db.py` (migration 14), `hub/app.py`, `hub/bus.py`, `hub/notify.py`, `hub/dashboard.py` (`event_summary`), `config.py` (`prompt_discussion_minutes`); create `hub/prompts.py`, `tests/test_prompts.py`.

**Interfaces — Produces:**
- Migration 14: `prompts(id INTEGER PRIMARY KEY, target TEXT NOT NULL, body TEXT NOT NULL, mode TEXT NOT NULL CHECK (mode IN ('single','group')), project TEXT REFERENCES projects(name), thread TEXT, status TEXT NOT NULL CHECK (status IN ('pending','running','discussing','done','failed')), created_by TEXT NOT NULL, created_at TEXT NOT NULL, finished_at TEXT)` and `prompt_recipients(prompt_id INTEGER NOT NULL REFERENCES prompts(id), agent_id TEXT NOT NULL REFERENCES agents(id), status TEXT NOT NULL CHECK (status IN ('pending','running','done','claimed','declined','skipped','timed_out','failed')), task_id INTEGER REFERENCES tasks(id), note TEXT NOT NULL DEFAULT '', updated_at TEXT NOT NULL, PRIMARY KEY (prompt_id, agent_id))` + indexes on `(agent_id, status)` and `(status, id)`.
- `prompts.create(conn, *, target, body, actor) -> dict` — body 1–8000 (strip; blank → `Invalid`); recipients from `views.recipients`; disconnected ones get `skipped`; mode `single` when exactly one live recipient, `group` when more, and `failed` with no live recipient; a group prompt's thread is project channel `prompt-<id>` (task and project targets) or the device board (device targets); the body is also posted as an operator private message to each live recipient (so their private chat shows it, labeled as a prompt); emits `prompt.created` `{prompt_id, agents: [live recipient ids], mode}` (no body).
- `prompts.pending_for(conn, agent)`, `prompts.start(conn, pid, agent)`, `prompts.finish(conn, pid, agent, *, ok: bool, note)`, `prompts.claim(conn, pid, agent, *, title, body) -> task` (group only; creates a task already approved — `state='open'`, created by the operator who made the prompt, the claiming agent added with role `Share of prompt #N`, stage `works`, default budget — and marks the recipient `claimed`; a second claim by the same agent → `Conflict`), `prompts.decline(conn, pid, agent, *, reason)`, `prompts.get(conn, pid)` (operator view: recipients, statuses, task links, thread key), `prompts.expire(conn, now)` (group discussions past `prompt_discussion_minutes`: undecided → `timed_out`), and the prompt becomes `done` once no recipient is `pending`/`running`.
- Agent API (active agent; own rows only, else 404): `GET /api/v1/prompts/pending`, `POST /api/v1/prompts/{id}/start`, `POST /api/v1/prompts/{id}/finish` `{ok, note}`, `POST /api/v1/prompts/{id}/claim` `{title, body}`, `POST /api/v1/prompts/{id}/decline` `{reason}`, `GET /api/v1/prompts/{id}` (recipient's view: body, mode, thread, co-recipients' names, statuses, devices and current tasks).
- Bus: `prompt.created` goes to its live recipients; `prompt.updated` (any status change) to the prompt's recipients. ntfy: a group prompt reaching `done`, or any recipient skipped/timed out/failed, notifies "Prompt #N: …" (names only).
- `prompts.expire` runs from the hub's existing periodic loop (or bus pump) every minute.

### Task 2: The runner runs prompts

**Files:** Modify `runner/daemon.py`, `runner/config.py` (`prompt_max_turns`, `prompt_wall_clock_minutes`), `runner/session.py` if needed, `client.py`, `examples/runner.example.toml`; tests in `tests/test_runner.py`, `tests/fake_claude.py` (a mode that records the prompt and, for group mode, calls the claim API like `review_approve` does).

**Interfaces — Consumes:** Task 1 API. **Produces:**
- The runner treats `prompt.created`/`prompt.updated` as a wake, and `sync()` also fetches `GET /api/v1/prompts/pending`.
- **Priority and busy rule:** a pending prompt runs as soon as a session slot is free and before any new task session starts (task loops wait while a prompt is queued); a running session is never interrupted.
- Working directory: task target → that project's checkout, resuming this agent's latest session on that task when one exists (`--resume`); project target → that project's checkout; agent or device target → the checkout of its current task's project, else its first configured checkout. No checkout → `finish(ok=False, note="no checkout configured for <project>")`.
- Session prompt: the operator's text outside the untrusted block under `From the operator (prompt #N, verified by the hub):`. Group mode adds instructions: read the thread and `prompt_status`, discuss with the other recipients as equals in the thread (project channel `prompt-<id>` via `post`, or the device board via `post_device`), weigh who is free or busy and what each machine has, agree a split, then call `claim_share` with a clear title and description for your part (or `decline_share` with a reason); do not start the work in this session — the share becomes a task you'll pick up next.
- Budget: `--max-turns prompt_max_turns`, wall clock `prompt_wall_clock_minutes`; usage limit → the same pause/resume as task sessions; the session outcome is reported with `finish`.
- After a runner restart, a prompt left `running` by this agent is resumed once; if it can't be, it's finished `failed` with a note.
